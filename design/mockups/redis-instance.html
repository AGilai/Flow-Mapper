Decisions

  1. Redis is in the Inventory like every other data store (frame 1): same toolbar, tabs, sub-chips and table. Only the row content is new: a kind chip (Redis cluster, Redis instance) and "7 services · 3 dbs · 12 key templates". The row opens the instance page.
  2. Order on the page follows the maintainer's direction: instance (identity, verdict) → who connects → keys. Keys are the last, lazy section.
  3. Who connects is lanes (service → access → client), one row per service. There is no instance node or fan: the page is the instance, and its summary (version, nodes, dbs, key templates) is in the head meta line. The #27 client sits in the last column; a click on a row docks the full client in a panel that squeezes the page.
  4. Keys load on request. The Keys section shows one sentence and a "Load keys" button. Counts and problems that are known without the list (from an instance summary†) already appear in the verdict, and the callouts link to "Load keys and show the row".
  5. Grouped by owner. The owner is the service that writes the template. A template written by several services is one row in a "Shared" group, never repeated under each writer. A template nobody harvested writes sits in "No harvested writer". Problem groups come first, then owners alphabetically.
  6. Filter: segmented db index control (All, db0, db1, db2, with counts), a search over the template text, and a "Problems" toggle. The db filter applies on the server, so an instance with thousands of templates loads one db at a time.
  7. Row = one template. Template, db, command kinds (writes in bold), ops per hour†, TTL†, and readers that are not the owner, named in full.
  8. Key → flows is an in-place expand (<details>), not a panel. It lists the entry points that write the key and the steps to the Redis call. Each entry links to the normal Flows tab (#/flows?service=X&ingress=Y); the inline chain is only a preview. These flows are derived from steps that already target the instance, if the step carries its key template†.
  9. Redis has no transport colour. Connectors and chips are neutral ink; --warn is used only for the two problem states.

Open questions

  1. What does the harvester emit per instance? Still unanswered by the reporter (#29 comment 95). Needed: key templates per service, read/write per template, TTL, db index.
  2. Does a step (type: resource) carry the key template? Without it, "flows that write this key" cannot be drawn.
  3. How is the instance identified: redis:cache-main from the bindKey, or the ElastiCache id? † Can db index be known per key, or only per client?
  4. Are op counts static (call sites) or measured (live)? A static count is "call sites", not ops per hour.
  5. Who owns a key written by two services: show both (decided), but should the page rank one as "primary"?
  6. How are non-code writers (Lua, other clusters, redis-cli jobs) declared, so "no harvested writer" can say "written outside code"?
  7. Do we keep key templates for pub/sub channels and streams? †
