Design environments: an HLD for the SASE project

Revision 4: frames 1–9 approved and built (0.24); frame 10 adds references (🔒), importing one level into a design, and partial-flow warnings. Frame 11, decided (rev 5): a pastel colour per component on heads and activation bars; arrows keep the transport colour (option A); colours assigned per environment and stored, so a component keeps its colour and there are no clashes up to 8; past 8 the palette repeats; neutral for client apps, externals and data stores. Static mockup for the maintainer. A design environment is a normal Flow-Mapper environment that holds a high-level design. You start it from any environment (prod, or another design), edit it on the canvas through shared drafts, sketch at subsystem level and refine down to components and endpoints, pull in what's missing from other environments while you work, and discuss any item. Names are illustrative. Tokens, chips, toolbar, tabs and the docked panel are the app's own (0.19.1).

  1. Status is computed, not stored. Every environment keeps the revision it was copied from (its baseline). The server compares the current state with the baseline at read time and marks each item New, Changed, Removed, or nothing (unchanged, "From prod" in the meta line).
  2. On every level. Subsystem link, component, endpoint, call, queue, message, a field of a message, a field of a collection. The mark goes on the highest new item only: a new component's endpoints are new by implication and don't repeat the icon, so the page doesn't fill with stars.
  3. The new icon is a small yellow spark, with one short twinkle when the page loads (off with reduced motion). It's the only yellow in the app: --warn stays amber and is never shown as a star.
  4. Words. Environment › subsystem › domain (later) › component › endpoint / message › field. A flow has a name ("Agent connects to POP"); the entry key is secondary. A draft is a named, shared set of changes that is applied in one step.
  5. Harvested environments stay read-only. Edit mode, drafts and import exist only in design environments.
--new (spark)--new-ink (outline, text)--warn (unchanged, amber)

Frame 4. Editing a flow in a draft

Frame 6. Importing what's missing while you work

Even a design that started Blank can pull in components and endpoints from other environments when it needs them. Three ways in: the assistant notices while drafting, a call points at something this environment lacks, or you search.

  1. The assistant checks as it drafts and asks once, with a short list: what matches, what exists elsewhere (import?), what exists nowhere (add as new). It never imports without asking.
  2. A call to something missing shows a neutral notice (not a problem: in a design it's normal) with "Import from prod" when another environment has it.
  3. Import from another environment searches every environment, groups results by environment, and says what comes along. Imports go into the open draft, so they're reviewed and applied like any edit. Their baseline is the source's current revision.
  4. Imported, not new. An imported endpoint is unchanged against its own source, so it gets no spark. The meta line says where it came from ("from prod, imported Oct 22").

Frame 10. References, importing one level, and partial flows

#/flows?env=sase-hld&draft=hld-import&tabs=sase-agent/in.tunnel.open&step=3. The agent's flow reaches two prod components whose behaviour isn't in the design: users-svc and activitylog. The user is about to import users-svc's posture endpoint so it can be changed.

  1. A reference has a lock. A copied endpoint without its behaviour (handler and call tree not in the design) shows 🔒 on its bar end, on its head and in lists, with the words "reference from prod". It's neutral, not a warning: referencing prod is normal in a design. A component with at least one reference endpoint shows the lock on its head; the panel says which endpoints.
  2. "Import into design" sits next to every lock: at the flow boundary, on the service page row, in the step panel. It never fires directly: it opens the preview on the right.
  3. One level, never recursive. The preview lists what comes along: the endpoint's handler and its call tree inside that component, the calls it makes, the stores it touches, the queues and DTOs it uses. What it calls in other components stays a reference (locked) and is listed under "Stays a reference", each with its own Import, so the next level is always an explicit choice.

  5. A partial flow says so. When any step of a flow continues into a reference, a neutral line under the step walk says "Partial flow: 2 steps continue into references", with the names and Import links. The flow list shows a small lock next to such flows.
  6. Editing across a reference warns once. Opening the edit form of a call whose other side is a reference shows a callout in the form: the edit changes the call only, not what happens in the reference. Frame 11. A colour per component (decided: option A, stored per environment)

Maintainer: "each component shall have its own colour on flows, so when jumping over the API it is clear what the in and out component is; same for its activation bar. I'm doubting about the link itself." Today every service head has a black stripe and every bar takes the colour of the call that reaches it, so a flow reads as lines of colour between identical black boxes. The idea: component colour says who, transport colour says how. Pastel fills, a deeper tone of the same hue only for the stripe and the bar outline.

  1. Who vs how. The head and the activation bar carry the component colour; the line, its arrowhead, the kind chip and channels (topics, queues) keep the transport colour. UI-GUIDE §2 and §8 stay true for everything that is a connection.
  2. Eight pastel slots, each tested against all ten transport tokens, status, --new and --accent in both themes. The hue wheel is already crowded by transports, so the colours are muted: most sit at least 7 apart from every token; cyan and ochre are the weak slots (4 to 6), see the table.
  3. Stable per name. Slot = hash(component name) mod 8, the same on every page. Two components of one flow on the same slot: the one whose name sorts later takes the next free slot, so the result doesn't depend on step order. Collisions are likely (about half of four-component flows), see open question.
  4. Who gets colour. Services, gateways, functions, workers: yes. Client apps and third-party externals: neutral grey, they are outside the system. Data stores: neutral. Topics and queues: transport colour, they are channels, not components.
  5. Nested bars (same component, deeper call) keep the hue and step one tone darker. Folds keep the dashed neutral body but carry the stripe at the top, so a folded component is still recognisable. Ingress middleware hatch, 🔒 reference dashes, the New spark and Changed ring are unchanged and sit on top of the component colour.
  6. Never the only cue. The name is on every head and the step bar names both ends with their dots. The colour helps the eye; it carries no information the text doesn't.
  7. Arrows: option A (recommended). The bars already show who is at each end of an arrow, so tinting the line as well adds noise and costs the transport reading.
  8. Legend of a flow lists only the components in it, each with its dot.

11c. The link itself: three options on the same flow

Same flow, same component colours on heads and bars. Only the arrows differ.

A. Transport colour recommended baseline

Readable: best. Two clean colour systems that never compete: the line is how, the bar is who. Lost: nothing; the caller colour is on the bar the line starts from. Conflicts: none with §2 or §8.

B. Transport line, caller dot, callee arrowhead

Readable: the dot and head repeat what the bars already say, and a coloured head hides the transport at the very spot the eye reads it. Lost: the arrowhead no longer matches its line. Conflicts: §2 (the connector is not fully transport coloured) and §8 (a transport token is no longer the only line colour).

C. Caller colour line, transport as chip

Storage, safety and reach

  • Stored as a sanitized HTML subset: p br strong em s ul ol li a table thead tbody tr th td span, with only href (http, https, mailto) on links and a class from the palette on spans. The server strips everything else, so what is shown is what was stored, and the client trusts nothing.
  • Colours are palette tokens, not hex: a coloured span stores class="cc-coral", and the class maps to the component palette tones (--cmp-*, contrast at least 4.4:1 on the surface in light, 7.4:1 in dark). A comment written in one theme stays readable in the other.
  • Paste keeps only the supported formatting: pasted HTML runs through the same filter in the browser, so bold, lists, links and tables from Word or a web page come across and fonts, sizes, backgrounds and hex colours are dropped.
  • MCP: list_comments (by env and flow, with since for polling) and add_comment (author, body as the same HTML subset or plain text, optional step and parent), so an assistant can read the discussion and answer in it.
  • Every environment has comments, harvested and design. A full copy of an environment copies its comments; Blank and Components copies do not.

  • Export is a menu on the flow header (Flows page, every environment, prod and the static preview included): "Copy Mermaid", "Download .mmd". Toast "Mermaid copied"; the download is named after the flow. Same text as GET /api/envs/:env/flows/mermaid and MCP export_mermaid.

Unmatched rows carry a warning icon and the bar above counts what will be created. Create-new components all go into one subsystem chosen once.
  • Re-import is idempotent: pasting the same text again finds the components, endpoints and calls it made, reuses them and adds nothing. Step 3 then shows "0 new" with the reused count.
  • MCP import_mermaid {env, draft, text, matches?, dryRun}: a dry run returns the proposed matches (the table's content) and the counts, so an agent can correct matches and send them back; without dryRun it appends the same edits to the draft.
  • Small screens (760 px): the dialog fills the width; each table row becomes a stacked card: participant and chip on top, the select full width below, the hint under it.

Rules and what follows

  • Owner is free text for now, the same naive identity as comments (the name remembered on this browser; suggestions are recent names). When accounts arrive it becomes an account picker and existing names are matched.
  • Numbers are per flow and never reused. Deleting #4 leaves a gap; the next item is #5. The number is what people say in a meeting.
  • Statuses: open (outlined dot, --ink-2), in progress (half dot, --accent), done (--ok), dropped (grey, struck through). Open and in progress count as "open" in headers and badges. An overdue due date uses --warn and says "overdue"; only open and in-progress items can be overdue.
  • The flow list shows a small badge with the count of open actions on a flow (hidden at 0).
  • MCP: list_action_items {env, service, ingress}, add_action_item {…, owner, description, status?, due?, step?, commentId?}, update_action_item {id, …}. An item added by an agent is marked "by AI", as comments are.
  • Later: an environment-wide "All action items" page with filters by owner, status and subsystem, alongside frame 8 (all discussions).
  • Full copy carries action items (with their comment links); Blank and Components copies do not.

Phases

  1. Environments and marks: envs table, copy from any source (Blank, Components, Full), subsystems, kind client, baseline and the computed New / Changed / Removed down to fields, frames 1, 2, 5, 7.
  2. Drafts and editing: drafts with apply and discard, panel forms, then direct editing on the diagram, flow names, import (frames 4, 6).
  3. Subsystem level: abstract links, refine, roll-up, the level control (frame 3).
  4. Discussions: threads on any anchor, the assistant's replies, the all-discussions page, per-call AI descriptions (frames 4, 8).

Decided (rev 2)

  1. Copy from any environment, Full copy included in phase 1; the label is "From <source>".
  2. New is a small yellow spark, computed by the server by comparing with the baseline, on every level down to a field.
  3. Neighbours one hop.
  4. Discuss anything, plus an all-discussions view later; flows get names.
  5. Full editing through shared named drafts; sharing and invites stay naive (free-text author) with room for members later.
  6. Subsystem-level abstraction with refine and roll-up.
  7. Import on demand from any environment, by the assistant or by hand.
  8. References and import (rev 4, frame 10): a copied endpoint without its behaviour is a 🔒 reference; "Import into design" copies one level (its own flow and what it uses), never recursively; continuations stay locked and partial flows and edits across a reference say so.
  9. Every flow page (rev 3): a wide collapsible flow description under the title, numbered steps with a ‹ › walk and a wide step description above the diagram, Squeeze on by default.
