RabbitMQ: topic exchanges, bindings and RPC over queues

Revision 2 (the maintainer's answers applied; see "Decided" at the end). Static mockup for the maintainer. Data: what the harvester found in a real Node service (namespace saferx): a topic exchange saferx.EventExchange with queues bound by key, and many in-house RPCv2 commands such as rpc.sxdns.dns.resolve. Five frames: two flow diagrams, the exchange page, the inventory and the RPC server's service page. Tokens, chips, toolbar, tabs and the docked panel are the app's own (0.17.3); the app rail is left out.

  1. AMQP colour: keep the token, retune it (decided, rev 2). --t-amqp already exists (violet #8a5cf0), but beside the indigo accent (links, "internal calls" pills, selected tab) and --flow-5 it reads as the same family. Now grape #8e44d6 light, #c58cff dark: 30° further from the accent, still clear of EventBridge pink and --flow-6, over 5:1 on white. RabbitMQ's brand orange is out: it is SNS.
  2. Grape is messages, olive is request and reply (decided, rev 2). Exchange publishes, queue deliveries, exchange and queue chips, the exchange page and inventory rows are grape --t-amqp. RPC over AMQP is olive --t-rpc everywhere: the arrow, the reply, the server's bar entered by RPC, the "amqp rpc" chip, the RPC ingress group, RPC inventory rows and panel accents. The chip and the panel still say the wire is AMQP. Frame 2b has both in one flow.

Frame 1. Flow: a publish to a topic exchange

#/flows?tabs=cp-middleware/in.deviceLogout. cp-middleware publishes device.{deviceId}.logout; 3 of the exchange's 5 bindings match, and a second publish matches none.

  1. Same chain as SNS. service → exchange lifeline → queue lifelines, one arrow per delivery, a single arrowhead at the queue. The diagram stops at the queue; consumers are the numbered rows under it, and tile N on the arrow is row N.
  2. Routing key once, on the trunk. It is drawn exactly as published, placeholder included ({deviceId} counts as one word). If the publish also names an event type, the label reads DeviceLoggedOut followed by the key in muted mono.
  3. The binding key is the branch marker (the filter marker of SNS): funnel icon plus the key, right after the fork. Both hops are AMQP, so the colour doesn't change at the exchange; the fork dot on the exchange lifeline marks the hop.
  4. Bindings that don't match are not drawn. As with SNS filters, a branch that the key doesn't route to doesn't exist in this flow. One muted line under the fork gives the count and the keys ("2 bindings don't match: audit.#, system.#") and links to the exchange page, where they are listed.
  5. No match: the arrow ends at the exchange with an amber "no binding matches" pill, the analogue of "no consumers". Its async heading says the message is dropped, or goes to the alternate exchange when one is declared (then the branch continues to that exchange).
  6. More than 4 matches: the 4th branch becomes "+N queues", and the async list holds all N rows, like the SNS fold.
  7. sendToQueue through the default exchange (decided, rev 2) is drawn straight service → queue lifeline, with no exchange lifeline and no marker, like an SQS send. Last row of the table below.

Frame 2. Flow: RPC over queues, drawn as a call

#/flows?tabs=swg-api/in.policyCheck, with the first RPC arrow selected and its panel docked on the right (it squeezes the diagram; it never overlays it).

  1. An RPC is a sync call. A solid olive (--t-rpc) arrow from the caller's bar into the server's bar, labelled with the command, then a dashed olive "reply". The command queue, reply queue and exchange are not lifelines: they are plumbing, and they live in the panel.
  2. The server gets a normal activation bar, coloured by what entered it: olive for an RPC, with its own stores, calls and nested RPCs. "Show inside sxdns" works as for HTTP.
  3. Chip "amqp rpc" under the command (the ⇄ icon means request and reply). It says the wire is AMQP; the olive colour says it is a call. A grape AMQP publish never has a reply and ends at a queue (frame 2b shows both side by side).
  4. Panel: command, caller and server with handler and source links, then the AMQP details (exchange, command queue, reply queue, correlation, timeout, library). Hover shows the same as a tooltip, in short.
  5. No harvested server: red dashed arrow to the "unresolved" lifeline, the command in red, the chip "no server harvested", and no reply, as unresolved HTTP today. The panel says which harvester to look for: the one that consumes rpcv2.policy.
  6. Timeout: when the harvester knows the call has a timeout handler, the reply reads "reply or timeout 5 s"; otherwise just "reply".

Frame 2b. Many RPC calls in one flow

cp-middleware's in.deviceSync (entered over HTTP) makes 7 RPC calls to 3 services, then publishes one event. Rules that keep it readable:

  1. The command is never shortened. It is the subject of the arrow. It wraps after a dot when it is wider than the hop.
  2. The chip shows once per caller and server pair (the first call); later calls to the same server get only the small ⇄ glyph at the arrow's start.
  3. Only the first reply per pair is labelled. The others are bare dashed returns, unless they have a timeout, which is always written.
  4. A call made in a loop is one arrow with "×3 loop", taken from the loop frame of the steps; it is not drawn three times.
  5. Olive and grape in one flow: the RPCs are olive with replies; the last row is a grape publish to saferx.EventExchange with no reply and no bar (queue lifelines folded in this frame).
  6. Toolbar "RPC replies: Show | Hide" (default Show). Hide turns each request and reply into a single arrow with a return tick on the server's bar, which halves the height of RPC-heavy flows.

Frame 3. Exchange page

#/instances/amqp%3Asaferx.EventExchange, the same pattern as the Redis instance page. The routing-key tester works (type a key).

  1. Head: name, grape kind chip with the exchange type, bind key in mono, provenance, then one line of AMQP facts (vhost, durable, alternate exchange).
  2. Verdict from the data, then one callout per problem: a published key that matches no binding (the message is dropped), and a binding that no harvested publisher feeds. Each ends with "Show the row".
  3. Publishers: one row per service and routing key, with what the key reaches. "Matches nothing" is the tinted problem cell.
  4. Bindings: binding key → queue → consumer and handler, plus "Matched by", the published keys that reach it. Bindings and queues are many to many: a queue bound twice gets one row per binding, grouped by queue.
  5. Test a routing key: type a concrete key; matching bindings get a grape left edge and the rest dim. The result line counts them. Topic rules: * is exactly one word and # is zero or more.
  6. Queue pages (amqp-queue:…) keep the existing channel layout (UI-GUIDE): exchange and binding key → this queue → consumer and handler.

Frame 4. Inventory: exchanges and queues, RPC plumbing folded

#/inventory, tab "Topics and queues", filtered to amqp.

  1. Exchanges and queues are ordinary rows with the grape kind chip; an exchange's chip carries its type. Connections reads in the kind's own words ("3 publishers, 5 bindings"; "bound by audit.#, 1 consumer").
  2. RPC queues are hidden by default. Command queues (rpcv2.sxdns) and reply queues are plumbing; the thing an engineer looks for is the command, which is listed as an entry point of its server (frame 5) and gets its own type "RPC command" in the All tab.
  3. One fold row says what is hidden and why, with "Show RPC queues". Shown, they are muted rows whose Connections names the commands they carry. Reply queues are never listed one by one (one per caller process); they appear as one row per caller.
  4. RPC rows are olive (decided, rev 2): RPC commands in their tab and the RPC queues when shown carry the olive chip; exchanges and queues stay grape.
  5. The kind filter gets "AMQP" next to the data-store chips, so exchanges, queues and RPC commands can be filtered together.

Frame 5. Service page: an RPC server's commands as entry points

#/services/sxdns, Connections tab, with the endpoint rpc.sxdns.dns.resolve selected (its panel is docked).

  1. Commands are ingress, like HTTP routes: an olive group "amqp rpc" with one row per command: the command in mono, its handler, and "from" the harvested callers. The group header names the command queue once.
  2. A command with no harvested caller says so in muted text ("no harvested caller"). It is not a problem: callers may be outside the harvest, and the server works without them.
  3. Egress mirrors it: sxdns's own RPC calls are an "amqp rpc" egress group, and its publishes sit in an "amqp" group with the routing key and the exchange.
  4. Endpoint panel: callers, each with its function, source link and timeout (callers often differ), the server's handler and the AMQP plumbing. "Trace a flow from here" opens the Flows tab on this command.
  5. Entry points list (Flows): RPC commands are listed under their service with the "amqp rpc" chip, like HTTP routes, so a flow can start at a command.

What the build needs from the contract

Today the schema has transport amqp, channel kinds amqp-exchange / amqp-queue, keys amqp:{exchange}/{routingKey} and amqp-queue:{queue}, glob bindings, and mode: sync on egress. That draws frame 1 already (DEMOS 0.17.0). The rest needs:

Decided (rev 2)

  1. AMQP colour: --t-amqp is retuned to grape (#8e44d6 light, #c58cff dark) for exchange publishes, queue deliveries, exchange and queue chips, the exchange page and inventory.
  2. RPC colour: olive --t-rpc for RPC over AMQP: arrow, reply, the server's bar, the chip, the RPC ingress group, RPC inventory rows and panel accents. Grape means messages on an exchange, olive means request and reply.
  3. RPC key: amqp-rpc:{command}.
  4. Non-matching bindings in a flow: kept as one muted line with the count and the keys.
  5. sendToQueue through the default exchange: drawn straight service → queue, no exchange lifeline, like SQS (frame 1 table).
  6. Route: the exchange page is #/instances/amqp%3A{name}.
