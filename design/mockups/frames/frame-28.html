Frame 28. Flows page: the diagram first (revision 3: two thin rows, three documents that can disappear)

Revision 3 follows the review: two rows (tabs, then a thin toolbar), the env description as a real document page, the flow description as a mini document, and all three description levels can disappear completely. With every description hidden the diagram starts …px from the top of the content area at 1900 and …px at 1280 (today about 310px). The flow doc is docked at the bottom (the existing Notes pane), so it does not move the diagram start: …px with it docked. A docked design doc lives in a right column and does not move it either: …px.

  1. Build on Notes (0.34, migration 017), no parallel feature. Notes is already one rich document per flow in table flow_notes(env, anchor, version, body…) with versions, history, restore, outline, a sticky tab row and a draggable splitter. The flow doc IS that document. The env doc is the same document with anchor env (no flow), same API (GET/PUT /api/envs/:env/notes?anchor=env), same editor, same History. No new table.
  2. What the sanitizer allowlist must grow (today: comment rich-text subset, h2/h3, step chip): h1, lists (nested), tables, code blocks, images, a Mermaid block (pre[data-mermaid], rendered client-side; the Mermaid import/export of #71 already speaks it), reference chips data-ref="svc|flow|call|step:<id>", and callout blocks div[data-callout=key|watch|risk][data-step]. The step badges in the diagram are derived from the callout blocks, so there is one source.
  3. Editor: the existing rich-text (block) editor, not Markdown. It is what Notes and comments already use and what the sanitizer protects; reviewers who are not engineers can use it; a "/" menu adds blocks. A read-only "Source" view (HTML or Markdown export) is a possible later add-on, not a second editor.
  4. Three levels, three places, one language. DESIGN / FLOW / CALL labels with icons; each can be docked, collapsed or hidden completely; hidden leaves at most a nav entry or a tiny icon, and View ▾ → Descriptions brings any of them back.
  5. Rejected: variant A, the two-row version with the design strip (old shots stay in the scratchpad).

Shop platform: high-level design

How the web client, catalog-svc, orders-svc and search-svc fit together, and which subsystem owns which data. A reading aid for the HLD review, not a deployment map.

Scope

  • In: the Shop and Catalog subsystems, their data stores, the client entry points.
  • Out: payments (own design), batch jobs, the admin tools.

Subsystems

SubsystemOwnsDataEntry points
Catalogproducts, reviewsmongodb:catalog-dbin.get.products.id.reviews, in.get.products
Ordersorders, payments hand-offpostgres:orders-dbin.post.orders
Searchquery indexderived from Catalog eventsin.get.search

Architecture

Key decisions

  1. Catalog owns product and review data. Orders reads Catalog only through its API, never its DB (see GET /products/{id}/reviews, step 1).
  2. Cross-subsystem events go over SNS/SQS, not direct calls.
  3. Reviews are read straight from MongoDB with no cache. Revisit if in.get.products.id.reviews shows up in the latency report.

Example: reading reviews

sequenceDiagram
  client->>catalog-svc: GET /products/{id}/reviews
  catalog-svc->>reviews: find({ productId })

Constraints

  • Reads under 200 ms p95.
  • No cross-subsystem DB access.
  • Every public entry point needs auth. One region.

FlowNotesComments 3Action items 1

Purpose

Returns the reviews of one product. Read-only: one find on catalog-db.reviews.

Key step 2

find on reviews is the only data-store access. The endpoint latency is this call.

Watch 1

The product id is not validated before the find, so a bad id returns an empty list, not a 404.

Risk 2

No pagination: every review of a hot product comes back in one find.

How it works

  1. 1 The client calls GET /products/{id}/reviews.
  2. 2 catalog-svc runs find({ productId }) on reviews.
  3. 3 The list goes back as 200 Review[].
