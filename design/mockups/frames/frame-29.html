Frame 29. Inventory: Drivers view (CR #130)

Which client library and version each component uses, per store type. Approved by the maintainer. It is built from what the server already returns (GET /api/envs/:env/clients: store, kind, service, driver, lib.driver, mixed, unresolved); the gaps are listed at the bottom. Names and numbers are mock data in the shape of the prod samples.

  1. Entry. One more tab at the end of the Inventory type row, after the data-store and AMQP groups: "Drivers" with a package icon (URL #/inventory?tab=drivers&store=redis). A tab, not a new nav item or modal: it answers an inventory question and shares the page head, the env and deep links.
  2. Table, not matrix, as the main view. The question is "who is on version X", so a row is package x version and its cell lists the components. A component x package matrix would be sparse (a component uses 1 or 2 of the 3 to 6 packages), grows with the number of components, and has no place for counts or "via wrapper". The matrix is kept for the other question, "what does this component use": Group by Component (29c), where it is dense, one row per component and one column per store type.
  3. Grouping. A store type is a segmented picker (one at a time, versions of different stores do not compare). Inside it, the table groups by package, newest version first, with a header row per package carrying the verdict pill ("2 majors in use: 5, 4") and totals. Columns: Version, Components (chips link to the component page; "2 res" when several resources; "mixed" when the same component carries two majors of the package), Resources, Operations, How it is reached (direct, or via the wrapper library, matching the existing lib.driver data). A row expands to its resources, each linking to the store page (29a).
  4. Highlighting rule. Per package inside the env: the highest major in use is the baseline. 1 major behind = thin amber bar, a faint tint and the words "1 major behind". 2 or more = red with "N majors behind". The baseline has no colour, so a healthy table stays quiet. Colour is never alone: the text always says it. It does not claim "outdated against npm": harvested data is the source of truth and no registry is queried.
  5. Filters and query. One query box plus three structured filters (Component, Package, Version) showing the same state as tokens. mongoose < 6 or redis 3 is parsed into tokens and equals picking them from the dropdowns. Version forms: < <= > >= =, a bare major (3, v3, 3.x) and ranges. "Only: mixed majors" is a toggle. The result keeps the table layout and the verdict sentence restates the query in words (29b). Queries live in the URL.
  6. Unresolved: own section, always below the table, never a filter and never hidden. Columns: component, resource, field, the harvester's candidates (dashed chips: guesses, not facts) and the reason in plain words plus the stable code. They are not counted in the version rows. Under a filter, a line says which unresolved entries are left out (29b).
  7. Per component. Two doors, one content: the Group by Component matrix (29c) and a right-hand drawer opened from any component chip, matrix row, or a new "Drivers" section on the component page. It lists the component's drivers across all store types with version, lag, how reached, and resource links.
  8. Any env. The picker is built from the store kinds that have clients in the current env. A kind with no client data is dimmed as "no data yet" and opens an explanation (29e), so SQS/SNS SDK and HTTP clients have a place before harvesters report them.

29a. Default: Redis, grouped by package, one version row expanded

The Drivers tab is active. Store-type picker, a verdict sentence, the query row, the table with amber bars on the 4.x and 3.x versions, the legend, and the Unresolved section. ioredis 4.28.5 is expanded to show resources (store links) and operations. catalog-svc shows the wrapper case: the ioredis inside saferxlib is 4.27.6 while its own driver version is unresolved.

What the build needs that does not exist yet

  1. Operations per client. /clients rows are per client site and carry no operation counts. Each row needs ops: {read, write} from the resource's steps or call sites (the graph has them).
  2. Aggregation. Grouping by package x version with component, resource and operation sums, plus the newest-major baseline and lag per package. listClients returns only counts by driver and major. A pure function in core/clients.ts (shared with the browser) or a /clients/drivers?kind= endpoint.
  3. Version comparison. Only majorOf exists and the filter is driver=pkg@major. The query needs a semver-like compare (range operators, minor and patch order for sorting), pure and tested with tags, git URLs, ^ and npm: forms.
  4. Unresolved candidates. unresolved[what=client] carries detail, reason, candidates and plain, but ClientRow keeps only field names and reasons. Candidates (the Mongo MG-a10 case) and plain must be passed through, and a client with no driver at all must still yield a row.
  5. Store types and packages. "SQS / SNS SDK" and "HTTP clients" need a client kind on egresses (egress client rows exist); the Mongo packages need only the MG-a10 data. The short package descriptions in the group header are optional: left out when not harvested.
  6. Component page. A "Drivers" section reusing clients-table.js plus the lag marks.
  7. Not drawn: loading and error states (the Inventory page's), the column sort menu, saved queries (URL only), widths above 1440 (the table widens), phone width.
