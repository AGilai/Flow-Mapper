Frame 31. Domain colour families (follow-up to #138, lifeline order)

With lifelines ordered domain > subsystem, colour should say the same thing: each domain gets one hue family, and its subsystems and components are close shades of it. Everything below is generated by one function from the real palette (--cmp-1..8), in light and dark. Try the Colour by switch in 31e: it recolours every drawing on the page. Data is invented.

  1. The rule (31a). Domain = the top-level group, in the env's group order. It takes the next hue from the existing palette, in a hue-spread order (blue, coral, green, violet, ochre, teal, pink, mauve) so neighbouring domains never look alike; past 8 domains the order repeats with lightness shifted. The stored per-component slot is not used for hue in this mode. In OKLCH: subsystem = base with a lightness step 0 / +0.07 / -0.07 / +0.13 in group order (signs flipped in dark), chroma x0.9 on shifted shades, hue +7° per step. Component inside a subsystem = a smaller step of 0.04 in the order 0, +2, -1, +3, -2 (alternating sign, so even the first neighbour pair is two steps apart) with 4° hue drift per step. A domain without subsystems (Agent) is one family whose components use the bigger step (0.05), having no subsystem step to lean on. Lightness is clamped to 0.40 to 0.66 (light) and 0.58 to 0.86 (dark) so a stripe keeps 3:1 against the surface.
  2. Neutral groups. "No group" is a flat neutral grey, External the same grey with a dashed header border. Neither takes a hue; components inside are told apart by name only (as client apps and infra are today).
  3. Contrast (31a). Text never sits on the family colour. As today, the header fill is the colour at 14% over the surface and the label is the normal ink, so the label stays far above 4.5:1 (each chip prints the measured number, the worst case is printed under each theme). The saturated shade appears only as the 6px top stripe, the activation bar and the dot, checked against the surface at 3:1 (non-text).
  4. Neighbours in a family (31b). Risk: a monotonic ramp of 5 shades has neighbours 0.04 apart in lightness, which reads as one colour. Fix: alternate the sign of the step (0, +2, -1, +3, -2) so adjacent lifelines differ by at least two steps, add the small hue drift, and let the stripe carry the shade (the header body stays at 14%). The measured neighbour distance (OKLab) is printed per chip. Colour is a grouping cue, never the only identifier: the name is always in the header and the bands name the group.
  5. Where each part takes its colour (31c, 31d). The lifeline line and the two band rows use the family colour (domain on row 1, subsystem on row 2, 22% fill, ink label). The header stripe, activation bars and step-caption dots use the component shade. System map (31f): domain frame = domain hue, subsystem frame = subsystem shade, box = component shade. In call order (31d) lifelines interleave, but each header still carries its family: the bands break into one cell per run and the three families stay distinguishable at a glance.
  6. Manual override wins (31c, 31e, 31f). A per-component colour override replaces that component's shade only: stripe, bar, dot, box. Its band and lifeline stay on the family. A small diamond on the header corner marks "custom colour", so a reader does not take it for a family member (tooltip: "custom colour, not from the family"). The colour popover gets a first option, Family (auto), which clears the override; palette slots and Custom stay as today. Overrides are stored per component, so they are not touched when the group order changes.
  7. The setting (31e). View menu, new group "Colour": a two-way switch Domain | Component, next to the lifeline-order toggle from #138. Component = today (stored slot per component, bands neutral). Default is Domain when lifelines are ordered by domain; the choice is remembered per user in the browser like the other View toggles. In call order with Domain, nothing else changes. Overrides apply in both modes.
  8. Not changed. Transport and status colours (UI-GUIDE section 8: colour is a component, never a transport or status). Hue follows group order, so inserting a domain in the middle of the order moves later domains' hues; only a re-order moves colours.
