Frame 18. Users and @mentions (new, bug #66)

Trigger: the Confluence importer brings review comments by “Einat Schanin” that mention “@Asaf Gilai”. Today an author is free text and a mention is plain text, so the import cannot say who wrote or who was addressed. Proposal (QA TL + lead): a small users registry, @mentions as chips, a Mentioned me view, and the same registry behind the action-item owner. No accounts or passwords: “who am I” is still a choice remembered on this browser.

  1. A user is a name, a colour and optional external ids. Avatar = initials on a tint of one of the eight component tones (--cmp-*, picked from a hash of the id, so it never changes with a rename). Users are created on first use: a comment author, an action-item owner, an import’s author or mention.
  2. A mention is a chip, stored as @[userId] in the body and drawn with the current display name, so a rename updates old comments. A chip for you is filled (accent); everyone else is a tinted pill. An id that no longer exists reads “@unknown user” in a dashed chip. Old plain “@Priya” text is left as text, never guessed.
  3. Imported authors keep their face and name and gain a small source mark (“C Confluence”). Hover or focus shows the external account id and where it came from.
  4. Where unread mentions live (my proposal): a global Mentions (3) entry in the left rail, next to Flows, opening a list across environments; plus a small “@ 1” badge on the flow’s row in the Flows list, and the Mentioned me filter in the Comments header. The rail entry is the one that answers “did anyone ask me something?” without knowing which flow. Unread = a mention newer than this viewer’s last visit to that comment thread (kept with the viewer, not in a shared table).
  5. The Users page sits under Settings in the rail. It lists, renames and merges. It never deletes: a user with history cannot vanish (that would orphan authors).

18a. Typing “@” in the composer opens the picker

The picker is an anchored popover under the caret; the typed text after “@” is the query (shown highlighted, as plain text until you choose). Matching is fuzzy over the display name and the aliases. With nothing typed yet it lists the people already in this thread first, then recent users. Enter or click inserts a chip and a space; Esc leaves the typed text as plain text. A new toolbar button “@ Mention” does the same for people who do not think of typing @.

Rules and open questions (Frame 18)

  • Identity is not security. “Who am I” is a remembered choice. Anyone can pick anyone; “you” on a comment still means “the remembered user equals the author”. Real sign-in is out of scope.
  • Users are created on first use, by exact external id first (authorExternalId + source, so a rename in Confluence does not fork a user), else by name ignoring case and spacing, else new. The importer’s mentions work the same way, which is how “Asaf Gilai” appeared next to the old “Asaf G.”.
  • Storage. A users table (id, name, colour slot, created, last seen), user_external_ids (user, source, external id, unique together), user_aliases (user, alias). Comment author and action-item owner become a user id; the old free-text author is kept as author_name for display when the user is gone. The body keeps @[userId]; the server resolves nothing at write time except to check the id exists. MCP add_comment accepts author as a name or user id, and mentions as @[id] or @Name (matched, else left as text).
  • Merge rewrites the ids on comments, replies, action items, mentions in bodies and the unread bookkeeping, in one transaction, after a backup. It keeps the dropped name as an alias by default (proposal), so history reads naturally and imports that still send the old name resolve. Not undoable from the UI. Open: should merging be allowed to anyone, since there is no sign-in? Proposal: yes, with the backup as the safety net.
  • Rename changes only the display name; chips and authors follow because they store ids. The old name is not kept as an alias unless asked (a checkbox in the rename row, off).
  • Notifications beyond the in-app badge (email, Slack, push) are out of scope. The assistant reads mentions through MCP (list_mentions {user, unread}, proposal).
  • Unread bookkeeping is per user and per comment (a small table of “seen” marks), not a count on the user, so it survives a merge and an edit that adds a mention to an old comment (it becomes unread).
  • Editing a mention out of a comment drops the unread mark; a mention in a deleted comment disappears from the Mentions page.
  • Open for the maintainer: (1) Is the rail “Mentions” entry the right home, or should mentions only be a badge on Flows? (2) Should an avatar picture (URL) be settable now, or later as agreed? (3) Do harvested environments show mentions too (comments exist in every environment)? Drawn as yes. (4) Should the assistant (MCP) be a user with its own colour, drawn as “Assistant”? (5) May a mention be of a group (“@everyone”)? Proposal: no, not now.
