Frame 19. Info pane for a component or a subsystem (new, bug #68)

Trigger: the importer doing HLD work wants to read, on the map and in a flow, what a component or a subsystem is: capabilities, why it exists, who owns it, what is still open. Data (0.30.2): an optional markdown about per component and per subsystem, by convention with five sections. The mockup draws the reading pane, the editor and the empty state. Status, links and relations are not typed in the about; they come from fields that already exist.

  1. One pane, extended (my proposal). Today's side panel (stats, “Called by”, “Calls”, Open service) is kept as the last section, “Connections”. The pane gains a header, the status mark, facts, About and Flows above it. Replacing it would lose the neighbour list people use to walk the graph; a second pane would fight for width. Edge and endpoint panels are unchanged.
  2. Right drawer, 420 px, resizable 340 to 640, drawn over the canvas’s right edge (the canvas gets narrower, it is never covered). It stays open while you click other items: the content swaps, scroll goes back to the top, the jump bar remembers nothing. Width is remembered per browser. Esc or × closes. A pin keeps it from closing when you click empty canvas (off by default).
  3. Same pane everywhere. Component: map (components level), a lifeline head in a flow, a row in a subsystem view. Subsystem: a box on the subsystems level, a band over the heads in a flow. Clicking a head still draws the halo and the pane header repeats the component colour, so the pane and the diagram point at the same thing.
  4. Header, then a jump bar, then sections. The jump bar (Overview · About · Flows · Connections) scrolls the pane; it is sticky. Sections are never collapsed behind tabs: a reader of a design review scans down the whole thing.
  5. The about is rendered, not shown as markdown. Each ## Heading becomes a labelled block with a quiet left rule. Open questions is the one block with a tint (warn colour plus a “?” marker, never colour alone) and its count is echoed in the header, because reviewers look for it first. Unknown headings render as ordinary blocks; text before the first heading is a lead paragraph.
  6. Status uses the existing marks: New (spark), Changed (ring dot), Removed (grey), Unchanged (outline, shown only at subsystem rows). A subsystem is “Changed” when any of its components is.
  7. Editing in design environments only, in the same pane: Edit turns About into a markdown editor; Save writes to the draft like other design edits. A harvested environment shows a read-only pane, with “Read-only” in place of the Edit button.

19i. Pencils everywhere: where you edit what is under a component (revision, maintainer feedback 2)

Answer to “where do I edit the descriptions and manual stuff?”: today only on the diagram in Edit mode. Now every editable thing in the pane carries a small pencil, so you never have to find the lifeline first. A pencil appears on hover of its row (always visible on touch) and opens the same form the diagram uses (web/js/design/edit-open.js): header pencil → component form (name, kind, subsystem, team; the facts rows share it); About section pencil → about editor scrolled to that section, the title-bar pencil edits the whole text; endpoint row → endpoint form; flow row → flow name and description; Docs pencil → links. The header keeps its text “Edit” button as the big target, which does the whole-about edit and turns every pencil on. Pencils are drawn visible here for review; one is shown hovered (accent).

  • Extend, not replace. One pane per selection; the old panel becomes “Connections” at the bottom. Edge, endpoint, step and queue panels are not changed. Component and subsystem are the only two kinds that get About.
  • Selection model. The pane follows the last click on a component, head, band or box. Clicking empty canvas closes it unless pinned. The URL carries sel=<component|subsystem> so a link opens the page with the pane (proposal; the flow view needs a way to say “head” vs “step”).
  • Keyboard. The pane is a labelled region. Opening it by keyboard moves focus to its title; Esc closes and returns focus to the node. In the editor, Esc asks before discarding.
  • Markdown-lite, sanitized at render, never at store. Headings (## and ###), lists, bold, italic, strike, inline code, links. Links must be http(s) or mailto and open in a new tab with noopener; anything else renders as text. Raw HTML and images are shown as text. The same renderer serves the pane, exports and MCP.
  • Section convention, not schema. The five names are matched ignoring case and a trailing colon. The pane only treats Open questions specially (tint and header count). Other headings render as plain blocks; order is the author’s.
  • Status comes from the design diff, not from the about. New, Changed (the about counts as a change of a prod component), Removed, Unchanged. In a harvested environment there is no status mark, only the “prod” label.
  • Edit scope. Only the about is edited in the pane. Docs links get a small inline form (main link, sub links) since #54 stores them as fields; team, kind and subsystem stay in Environment settings and the Inventory. Save to draft writes one design edit; two people editing the same about in one draft: last save wins with a “changed by someone else” prompt (proposal, same rule as comments).
  • Long abouts. The About block is never truncated in the pane. In row summaries (19b, Inventory) the first non-heading line is used, cut at about 90 characters.
  • Related flows are computed from calls, not stored: any flow whose steps touch the component; for a subsystem, any flow touching any of its components, with a count of components involved.
