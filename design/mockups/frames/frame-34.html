Frame 34. One field: type

Maintainer decision: replace today's mix (service kind for the look, details.icon from #144, details.product from #148, store and channel kinds) with a single type that has two levels. Data is invented.

  1. Two levels (34a). A generic type (service, idp, vault, database, cache, queue, topic, storage, search, function, container, gateway, cdn, workflow) says what the component is and shows a generic icon. A specific type belongs to exactly one generic type (auth0 is an idp, postgres a database, aws-sqs a queue) and shows the vendor's official logo.
  2. Icons are all official. Generic icons are the AWS Architecture Icons "General" resource icons (Light file on light theme, Dark file on dark theme, never edited). Specific icons are the brand set from frame 32 plus the official Kubernetes logo (Devicon 2.16.0). Nothing is drawn by hand. The AWS package has no dedicated icon for cache, topic, function, container, gateway, cdn and workflow, so those use the closest general icon (cache = Data-Table, topic = Forums, function = Source-Code, container = Servers, gateway = Internet, cdn = Globe, workflow = Gear). Maintainer to confirm, or name a better official one.
  3. Heads (34b). As in 0.66.3/0.67.0: a typed head, generic or specific, is a large centred icon (30px) with the name only under it. An untyped head keeps name plus "service" in grey. A generic icon is drawn in ink, so a head with a generic type reads as "a kind of thing" and one with a logo as "this product".
  4. Info pane (34c). One Type row replaces the Icon and Product rows: "IDP · Auth0" (generic, then specific, with the small logo), or just "IDP" for a generic-only type. Editing it is one two-step picker: generic first, then optionally a specific one under it.
  5. Manifest and fallbacks (34d). "type": "auth0" replaces details.icon and details.product. An unknown value renders as service. Old data still reads: details.icon: "vault" is taken as the type, kind stays for flow behaviour only.
