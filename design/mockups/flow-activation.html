Flows: activation bars, flow tabs, drill-down, descriptions

Static mockup, no JS. Data: live prod traces of api-gateway · in.createOrder, account-lambda-erase-controller · in.advanceErase and saga-controller · in.start. Tokens, chips, toolbar, context menu and panel shell are the existing ones; the app rail is left out. Revision 4. Earlier card frames are in git history (c564ad5, 1337268).

Diagram rules

  1. A call into a service is one activation bar spanning the whole call, from the incoming arrow to the last outgoing arrow or response. Chained internal calls are not drawn; a pill says "N internal calls ▸". Bar colour = the transport that entered it. A service called twice gets a separate bar per call.
  2. No arrow crosses an unrelated bar. Nested async work never interleaves in a parent's bar; it opens in its own tab.
  3. Topics and queues have no bar. They are the dotted "published events" rail and chips. A fan-out is a plain heading row in the list of flows.
  4. Sync: solid request, dashed return (status, or just "return"). No match or unresolved: red dashed arrow to the "unresolved" lifeline, no return. Data stores are stubs on the bar.

Tabs: every flow is a tab, there is no "main" flow

  1. All tabs are equal and closable. The strip sits under the toolbar. The first tab is the entry point picked in the Flows list; picking another entry point in the list opens another tab (it never replaces one); an already open entry point just activates its tab. Async sub-flows and "Start a full flow from here" open tabs too. Closing the last tab leaves the empty state "Pick an entry point" (frame below).
  2. Tab labels. Entry-point tab: service · ingress with an "enter" icon and an http-blue top edge. Sub-flow tab: number · consumer · handler (nested 3.1) with the delivery's transport colour on top. Full-flow tab: ⤓ icon, accent edge. Width 130 to 230px with ellipsis, full text in the tooltip, ✕ or middle-click closes.
  3. Breadcrumb on sub-flow and full-flow tabs only: origin tab › publish step › this flow. Each part jumps to the origin tab, which is re-opened if it was closed.
  4. Index under a diagram (default: nothing opens by itself): one 40px row per consumer flow; click opens its tab; a dot = already open; "Full flow ▸" starts a full flow from there. Open all opens one tab per distinct consumer only. Repeats stay as "↩ seen in tab N" rows with "Jump to tab N".
  5. Suspect rows: if one publish reaches the same consumer and handler more than once, the row gets a warn chip "suspect" with the tooltip "Same consumer reached twice by one publish. Possible harvester or config bug." (illustrative row in frame 3; the live trace has none).
  6. Tab memory: each tab keeps its scroll position, selected bar and open drill-down; closing a tab activates its neighbour to the left (or the origin tab of a sub-flow).
  7. Overflow (12 tabs): the strip scrolls with fading edges and ‹ › buttons, the active tab stays in view, "▾ 12" lists all tabs with a filter, "Close others" and "Close all".
  8. Keyboard (no clash with Ctrl/⌘+W, Ctrl+Tab, Alt+←): in the diagram or tab strip, [ and ] previous/next tab, 1 to 9 tab N, Alt+W close, Alt+Shift+T reopen the last closed. ARIA tablist: arrows move between tabs, Delete closes. Esc closes the right drill-down panel only, never a tab.
  9. URL: #/flows?tabs=api-gateway/in.createOrder,sqs:shipping-order-events/onOrderPlaced@api-gateway/in.createOrder,…&tab=…. tabs lists all tabs in order: entry-point tabs keyed service/ingress, sub-flows keyed delivery (queue/handler) plus their origin key, full-flow tabs full:service/handler. Display numbers are never in the URL. Tab switches replace the URL state (Back leaves the page). Unknown keys are dropped silently. Links with the old service=&ingress= form open one entry-point tab.
  10. Opening animation: the current flow shrinks to the LEFT into its own tab, then the new tab's panel comes in. 140 ms: diagram scales to about 0.6, then 0, origin top-left, translate left, opacity 1 to 0, ease-in-out cubic-bezier(.4,0,.2,1); the new tab grows from width 0. Then 140 ms, ease-out cubic-bezier(.2,.7,.2,1): the new flow fades in and slides 12px from the right. Total 280 ms. Switching between tabs is a 120 ms cross-fade. Reduced motion: no transform, one 80 ms cross-fade.
  11. Toolbar: "Inside the service | Full flow", "Data stores", "Frontier steps", "Depth" stay; "Internal calls" goes away; "Queues and topics" adds queue/topic lifelines in sub-flow tabs (off by default). Inside the service keeps the publish badge, one leg only.

Drill-down and alt frames (decided)

  1. Drill-down lists only the functions this flow runs (handler plus its chain), with the link "All N functions of X ›" to the service page. Double-click a bar or right-click → "Show inside X"; 380px panel on the right; Esc or ✕ closes.
  2. Alt frames in the panel: same UML frame as in the diagram around the function's steps. Heading = alt group name + branch count; one section per branch with the condition text only as heading; each step has its code link; each publish links to its rail arrow and tabs. Orange dots A to H explain the manifest fields in the table under frame 2c (mockup only).

Descriptions: two containers, Human and AI

  1. Where: flow description as a block at the top of an entry-point tab; sub-flow description as a one-line under the breadcrumb of a sub-flow tab, a block under the header of the drill-down panel, and a hover popover on a bar (400 ms delay, keyboard focus too).
  2. Two containers each: Human (green edge; shown first when present; only humans edit it, "Edit" or "Add a note") and AI (accent edge; collapsible under it; written only by an AI tool; no Edit, only "Generate…" to replace). One-line variant: the Human text if there is one, else the AI text.
  3. "Generate…" does not call an AI. It opens a dialog with a ready-to-copy prompt for any AI harness (Claude Code, Cursor, …): use the Flow-Mapper MCP server, read the flow with trace_flow and each callee with get_service, write the text, save it with a write tool. Copy button and the note "paste into an AI tool that has the Flow-Mapper MCP connected" (frame below).
  4. API needs (no implementation): two records per key, source = human | ai. Key: env + service + ingress for the flow, plus callee for a sub-flow (the service, or service:handler for a delivery). Human record: text, edited_by, edited_at. AI record: text, model, generated_at, trace_hash (the UI flags "outdated" when it differs from the current trace). New MCP write tool set_description(env, service, ingress, callee?, text, model) writes the AI record only; humans write theirs through the UI/REST. Neither record overwrites the other. Reads come with the trace.

Why it exists: turn a checkout click into a paid, stock-backed order, and keep slow follow-up work (shipments, emails) out of the customer's wait.

Generate a description with your AI tool

Flow-Mapper does not call an AI itself. Copy the prompt and paste it into an AI tool that has the Flow-Mapper MCP server connected (Claude Code, Cursor, and so on). The tool reads the flow through MCP and saves the text back.

prod
You are documenting a flow in Flow-Mapper. Use the Flow-Mapper MCP server.

Target: env "prod", service "api-gateway", ingress "in.createOrder" (the whole flow).

1. Call trace_flow(env="prod", service="api-gateway", ingress="in.createOrder", scope="full")
   and read every step, activation bar and async consumer in it.
2. For each service that appears, call get_service(env="prod", service=<name>)
   for its description, owner and functions.
3. Write (a) the flow description: the motivation and purpose of the whole flow, 2 to 4
   plain sentences, then one sentence starting "Why it exists:"; and (b) for each service
   sub-flow: what that service does in this flow and why, 1 to 2 sentences.
   Use only facts found in the trace and the service records. Do not invent anything.
4. Save each text with set_description(env="prod", service="api-gateway",
   ingress="in.createOrder", callee=<omit for the whole flow; "orders-svc" or
   "shipping-svc:onOrderPlaced" for a sub-flow>, text=<your text>, model=<your model name>).
5. Reply with one line per description you saved.
Writes only the AI description. The Human note is never touched.
